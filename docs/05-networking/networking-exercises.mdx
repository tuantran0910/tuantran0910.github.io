## Diagnose from the same source Pod

For each case, pick the next test before revealing the explanation. Assume the application expects the same HTTP host and path for each probe.

<details>
<summary>The name returns NXDOMAIN, and the ClusterIP returns HTTP 200.</summary>

Inspect the source Pod's DNS search domains and verify the Service name, namespace, and cluster domain. This request reaches the Service successfully by address.

</details>

<details>
<summary>The name resolves, the ClusterIP times out, and the backend Pod IP returns HTTP 200.</summary>

Compare Service port and targetPort with the EndpointSlice ports and endpoint conditions. Check Service forwarding and policy evaluation. A single successful backend test proves only that one path works.

</details>

<details>
<summary>Internal HTTP requests work, but the public gateway returns 502.</summary>

Check the route parent conditions, the configured upstream protocol and port, and load balancer health. Identify the upstream selected by the gateway and use its logs to narrow down the failure.

</details>

## Calculate GKE Pod IP capacity

Start with a /16 and 110 Pods per node. Compare the result with 64 Pods per node. The model assumes one homogeneous IPv4 Pod secondary range and uses the documented block allocation formula. Primary subnet capacity, system Pods, quotas, mixed pools, and upgrade headroom affect usable capacity.
